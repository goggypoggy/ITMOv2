# GitHub Spec Kit vs OpenSpec — сравнение на примере фичи «Сброс уровня»

Процесс
- OpenSpec: единый управляемый цикл (new/validate → design → apply/tests → archive). CLI даёт статус, инструкции и проверяет структуру. Хорош для brownfield‑изменений с требованием прослеживаемости.
- GitHub Spec Kit: фокус на форме и полноте спеки (UI/Logic/Contract), гибче процесс, без встроенного CLI. Хорош для параллельной работы двух подкоманд до кода.

Артефакты
- OpenSpec: proposal.md, design.md с проектными правилами (Mermaid), архив, config.yaml (rules), подтверждения CLI (list/show/validate/view, instructions, archive).
- GHSK: UI спека, Logic спека, Contract, версии «до/после» и их diff.

Трудозатраты и удобство
- OpenSpec: выше порог входа (CLI, схемы), но меньше «потерь шага» — видно, что пропущено; легко приложить доказательства.
- GHSK: ниже порог, удобно раскладывать ответственность; требуется дисциплина для фиксации «до/после» и контракта.

Риски и плюсы
- OpenSpec: плюс — строгая трассируемость; риск — излишняя формальность для микроизменений.
- GHSK: плюс — гибкость и наглядность для разных ролей; риск — отсутствие автоматической проверки целостности.

Вывод по фиче «Сброс уровня»
- OpenSpec позволил минимально и прозрачно провести изменение (skip_specs: true), заархивировать и подтвердить правила.
- GHSK помог заранее разделить UI/Логику, зафиксировать контракт и идемпотентность, что обеспечило чёткие тесты и быстрое согласование.
