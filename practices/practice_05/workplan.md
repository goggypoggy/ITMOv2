# План работ по практике 5

Цель: провести одну фичу проекта из practices/practice_04 через полный цикл OpenSpec, затем настроить правило OpenSpec под проект и выполнить ДЗ с использованием второго SDD-фреймворка — GitHub Spec Kit — для подготовки двух согласованных спецификаций (UI и логика) с последующей реализацией.

## Базовый проект

- Рабочий код: practices/practice_04 (одностраничный лэндинг с двумя фичами: переключатель уровня и калькулятор времени).
- Команды проекта:
  - Запуск тестов: `npm test` (в каталоге practices/practice_04).
  - Локальный сервер: `npx --yes serve -l 8080 .` (в каталоге practices/practice_04), открыть http://localhost:8080/.

## Предварительные условия

1. Node.js ≥ 20.19.0: `node --version`.
2. Установка OpenSpec CLI 1.14.1 глобально: `npm install -g @fission-ai/openspec@1.14.1` и проверка `openspec --version`.
3. Инициализация OpenSpec в корне проекта, где будет идти разработка: в practices/practice_04 выполнить `openspec init --profile core` и выбрать текущий клиент.
4. Проверить список воркфлоу: `openspec list --json`.

## Часть 1. Полный цикл OpenSpec для одной фичи

1. Выбор небольшой фичи в рамках текущего UI без расширения архитектуры. Примеры на выбор:
   - Сброс выбранного уровня до значения по умолчанию и синхронное обновление «Программы» и «Тарифов».
   - Копирование рассчитанного ETA и плана в буфер обмена из калькулятора.
   - Подсветка некорректного ввода часов (>40 или 0) с текстовой подсказкой без всплывающих окон.
   - Сортировка модулей «Программы» по сложности для выбранного уровня.
2. Исследование кода и проверок через OpenSpec: запустить `/opsx-explore` (Codex: `$openspec-explore`). На этом шаге код не меняется.
   - Зафиксировать текущее поведение и границы, придумать 3–5 условий приёмки и негативные сценарии.
   - Запустить baseline тестов проекта: `npm test` (в practices/practice_04).
3. Создание предложения спецификации: `/opsx-propose <feature-key>` (Codex: `$openspec-propose`). Передать цель, условия приёмки, границы и «что не входит».
   - Проверка в CLI: `openspec list`, `openspec list --specs`, `openspec show CHANGE --type change`, `openspec validate CHANGE --type change --strict --no-interactive`, `openspec view`.
4. Review и уточнение: отдельная проверка предложения (без правки кода). При необходимости — `/opsx-update <feature-key>` с согласованными правками.
5. Реализация: `/opsx-apply <feature-key>` (Codex: `$openspec-apply-change`) только после принятия спеки. Агент вносит изменения в practices/practice_04 в согласованных границах.
6. Проверки после реализации:
   - Автотесты Playwright: `npm test` (в practices/practice_04).
   - Ручная проверка: локальный сервер, переключение уровней/изменение входов калькулятора, отсутствие ошибок в DevTools.
   - Для каждого сценария собрать связку «ожидание → факт → доказательство (лог, скрин, вывод тестов)».
7. Приёмка человеком: сопоставить условия приёмки и фактические результаты. При необходимости — возврат на шаг 4 с уточнением спеки и повторным apply.
8. Актуализация спеки и архивирование: `/opsx-sync <feature-key>` (Codex: `$openspec-sync-specs`) и `/opsx-archive <feature-key>` (Codex: `$openspec-archive-change`).

Готово, когда: фича реализована в согласованных границах, автотесты зелёные, ручная проверка пройдена, спеки синхронизированы и заархивированы.

## Часть 2. Настройка правила OpenSpec под проект

9. Подготовить следующее изменение (черновик) через `/opsx-propose <next-feature>` и остановиться до apply. Сохранить «до»-версию фрагмента design или spec.
10. Добавить правило в конфигурацию OpenSpec проекта (объединить с существующим `openspec/config.yaml`, не создавая второй `rules`):
    - Для design:
      - `rules.design: - Объясни взаимодействие диаграммой Mermaid.`
    - Если design не требуется, использовать `rules.specs` и формат Given/When/Then для существующей spec.
11. Проверка инструкции правила перед обновлением: `openspec instructions design --change <next-feature> --json`.
12. Применение правила к тому же фрагменту через `/opsx-update <next-feature>` (Codex: `$openspec-update-change`), просмотр diff «до/после», подтверждение человеком. Код не меняется.
13. Зафиксировать результат: сохранить «после»-версию фрагмента и вывод проверки правила.

Готово, когда: правило добавлено и проверено на одном фрагменте; смысл сохранён, форма изменилась по правилу.

## Домашняя работа. Второй SDD‑фреймворк: GitHub Spec Kit

14. Подготовка среды для GitHub Spec Kit:
    - Определить место хранения документов (репозиторно): `practices/practice_05/specs-ghsk/`.
    - Взять структуру разделов GitHub Spec Kit (разделы спецификаций, термины, чек‑листы) и адаптировать под локальные Markdown‑файлы. Если используется шаблон/генератор, следовать его документации; если нет — создать Markdown по разделам вручную.
15. Две спецификации до кода по одной фиче (другая, либо развитие фичи из части 1):
    - Команда 1 — UI спецификация: сценарии экранов и действий, состояния и ошибки, макеты/описание состояний, ограничения доступности.
    - Команда 2 — Логическая спецификация: данные и алгоритм, API/контракты, правила и валидация, ошибки и граничные условия.
    - Обе — со списком измеримых условий приёмки и негативных сценариев. Явно указать «вне рамок».
16. Согласование общего контракта:
    - Сверить данные, вызовы, ошибки и состояния между UI и логикой.
    - Оформить `contract.md` (в `specs-ghsk/`): таблица/перечень входов/выходов, форматов, кодов ошибок, инвариантов.
    - Обновить обе спеки до согласованной версии («после согласования»).
17. Реализация по согласованным спекам в practices/practice_04:
    - Внести изменения в UI/логику в рамках согласованных границ.
    - Обновить/добавить тесты: сквозной сценарий и ошибка/граница (использовать Playwright тесты из `tests/`).
    - Проверка: `npm test` и ручное демо на локальном сервере.

Готово, когда: две согласованные спеки (до/после), общий контракт, реализованный код и проверки, демо, рефлексия.

## Что подготовить к сдаче

- Спеки OpenSpec: change/spec до/после, подтверждения CLI (validate/view, архивирование).
- Правило OpenSpec и подтверждение его срабатывания (инструкции и diff фрагмента).
- GitHub Spec Kit:
  - UI‑спека и логическая спека (до/после согласования).
  - Общий контракт `contract.md`.
- Код изменений в practices/practice_04, результаты проверок (вывод `npm test`, доказательства сценариев).
- Короткое демо (скриншоты/видео или повторяемые шаги локально).
- METAREPORT.md: отчёт об агентской работе - какие были изменены файлы, какие промпты были прописаны человеком.

## Контрольные точки и риски

- На каждом шаге фиксировать «ожидание → факт → доказательство»; не переходить к реализации без принятой спеки.
- Не расширять границы фичи в apply; при новых фактах — возврат к propose/update.
- В OpenSpec не плодить несколько блоков `rules`; править существующий.
- Для GitHub Spec Kit — не смешивать UI и бизнес‑логику; контракт ведётся отдельно и синхронизируется в обеих спеках.
