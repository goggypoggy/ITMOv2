# Роли и ответственность

Основано на подзадачах из practices/practice_05/workplan.md: полный цикл OpenSpec, настройка правила OpenSpec, подготовка двух спецификаций в GitHub Spec Kit (UI и логика), согласование контракта, реализация и проверки в practices/practice_04.

## Роли (5)

1. Владелец продукта (Product Owner)
   - Определяет цель фичи, границы и приоритеты; формулирует 3–5 условий приёмки и негативные сценарии.
   - Участвует в explore/propose обсуждении, отвечает на вопросы, фиксирует «что не входит».
   - Принимает результат после проверок: сопоставляет условия приёмки с фактом и даёт разрешение на archive.
   - Разрешает спорные моменты при согласовании UI и логики; утверждает общий контракт.
   - Навыки: предметная область, формулирование требований, принятие решений, базовое понимание UX и ограничений фронтенда.

2. SDD‑фасилитатор (OpenSpec/GitHub Spec Kit)
   - Ведёт цикл OpenSpec: запускает `/opsx-explore`, `/opsx-propose`, `/opsx-update`, `/opsx-apply`, `/opsx-sync`, `/opsx-archive`; проверяет `openspec list/show/validate/view`.
   - Подготавливает и поддерживает документы change/spec; собирает доказательства «ожидание → факт → доказательство».
   - Настраивает проектное правило в `openspec/config.yaml`, проверяет `openspec instructions … --json`, показывает и согласует diff формы без изменения смысла.
   - Организует работу с GitHub Spec Kit: структура папок, шаблоны разделов, контроль качества спеки, выпуск `contract.md` и версий «до/после».
   - Навыки: OpenSpec CLI, GitHub Spec Kit, Git/Markdown, Mermaid, системное и контрактное мышление, CLI/Node.js базово.

3. Инженер UI (Frontend UI)
   - Автор UI‑спеки в GitHub Spec Kit: экраны и действия, состояния и ошибки, ограничения доступности, измеримые условия приёмки.
   - Реализует UI‑изменения в `practices/practice_04` (HTML/CSS/JS ES‑модули), интеграция с `level-switcher` и визуальные состояния.
   - Обеспечивает адаптивность и отсутствие ошибок в консоли; готовит демо.
   - Участвует в explore/propose, предоставляет ограничения UI и влияния на существующие элементы.
   - Навыки: HTML5, CSS, ванильный JavaScript (DOM, события, модули), UX‑паттерны, адаптивная верстка.

4. Инженер логики (Frontend Logic)
   - Автор логической спеки в GitHub Spec Kit: данные, алгоритмы, правила валидации, интерфейсы модулей и форматы.
   - Реализует логику и данные в `src/components` и `src/data` без изменения архитектурных границ; обрабатывает граничные случаи.
   - Участвует в согласовании общего контракта UI↔логика, синхронизирует спецификации «до/после».
   - Навыки: JavaScript (ES‑модули), проектирование модулей, алгоритмы, валидация, контракт‑ориентированное проектирование.

5. Инженер по тестированию (QA/Automation)
   - Ведёт baseline и итоговые проверки: `npm test` (Playwright), анализ падений, triage.
   - Добавляет/обновляет автотесты: сквозной сценарий и ошибка/граница; проверяет сохранение старого поведения.
   - Проводит независимую приёмку: основной, ошибочный и регрессионный сценарии с фиксацией «ожидание → факт → доказательство»; без правок файлов.
   - Поддерживает ручное демо: локальный сервер, DevTools, отсутствие ошибок в консоли.
   - Навыки: Playwright, тест‑дизайн, отладка браузера, CI‑совместимость, базовый HTML/CSS/JS для понимания DOM.

## Соответствие задачам плана

- Explore/Propose/Update/Apply/Sync/Archive: SDD‑фасилитатор (+ввод от Владелец продукта; реализация инженерами UI/логики; приёмка Владелец продукта; независимая проверка QA).
- Добавление правила OpenSpec и проверка формы: SDD‑фасилитатор, согласование с Владелец продукта.
- GitHub Spec Kit: UI‑спека — Инженер UI; логическая спека — Инженер логики; контракт — совместно UI/Логика под фасилитацией SDD‑фасилитатора; review на проверяемость — QA.
- Реализация и проверки в practices/practice_04: Инженер UI и Инженер логики; автотесты и приёмка — QA; финальная приёмка — Владелец продукта.
