## Базовые требования

При выполнении практики необходимо делать всё пошагово.
Разрешено и желательно запускать субагентов на отдельные подзадачи.

Все этапы и выполняемые шаги необходимо отразить в REPORT.md.

## Конкретика для лабораторной работы 6

### Глобальные этапы

1. Найти уязвимости до правок (инициальная модель угроз, статический и динамический анализ, доказательства эксплуатации).
2. Внести правки, чтобы запатчить уязвимости (минимальные изменения, сохранение функциональности, авто‑тесты).
3. Повторно попытаться найти уязвимости после фиксов (регрессия и негативные проверки, итоговый отчёт).

### Роли и субагенты

- Координатор: управляет агентской работой, собирает артефакты, формирует REPORT_01/REPORT_02.
- Аналитик (статический): читает код `service.py`, составляет список угроз и гипотез атак.
- Эксплуататор (динамический): запускает сервис, воспроизводит эксплойты, сохраняет доказательства.
- Фиксер: реализует минимальные правки, покрывает тестами, сохраняет совместимость.
- Судья: запускает LLM‑проверку prompt injection по инструкции из `README.md` и фиксирует результаты.

### Детализация по шагам

Этап 1. Инициальное обнаружение уязвимостей

- Подготовка окружения
  - Запустить тесты: `make -C practices/practice_06/lab install && make -C practices/practice_06/lab test`.
  - Запустить сервис: `python3 practices/practice_06/lab/service.py --port 8066`.
  - Зафиксировать адрес и порт. Если занят — выбрать другой и указать в REPORT.

- Модель угроз и поверхность атаки
  - Составить список эндпоинтов из `lab/README.md` и кода `service.py`.
  - Идентифицировать активы: профили, заказы, файлы стенда, токены, роли, инструменты ассистента.
  - Определить доверенные границы: HTTP‑процесс, SQLite, Sandbox (граница файлового стенда), LLM‑ассистент.

- Статический анализ кода (`service.py`) и гипотезы
  - SQL‑инъекции: `GET /profile` (вставка `id`), `GET /search` (вставка `q`).
  - IDOR/разглашение: `GET /orders` (все заказы без аутентификации/авторизации).
  - Эскалация ролей: `GET /admin/export` через заголовок `X-Role` вместо сессии.
  - Подмена цены: `POST /orders` принимает `price` от клиента.
  - Чтение файлов чужих пользователей: `GET /files` принимает `user` и `path` без связи с сессией.
  - Утечка токенов: `GET /debug/logs` выдаёт логи с заголовками (`X-Token`).
  - XSS/Prompt Injection: `POST /reviews` + `GET /reviews/view` (несанитизированный HTML), включение отзывов в `/assistant/context`.
  - Неавторизованный доступ к инструментам: `POST /assistant/execute` не проверяет токен/роль, позволяет `export_profiles`/`delete_tree` любому.

- Динамическая валидация гипотез (эксплойты) — сохранить вход/выход в `practices/practice_06/evidence/before/`
  - SQLi в `/profile` и `/search`: показать извлечение всех профилей/ошибки типа UNION/OR '1'='1'.
  - Доступ к чужим/всем заказам через `/orders` без токена.
  - Эскалация через `X-Role: staff` на `/admin/export` без сессии.
  - Чтение чужих чеков через `/files?user=bob&path=receipt.txt` под `alice` или без токена.
  - Подмена цены в `/orders` (создание заказа с заниженной ценой).
  - Утечка токенов через `/debug/logs`; повторное использование токена из логов.
  - Prompt injection: добавить отзыв с вредной инструкцией, получить `/assistant/context`, запустить `shop-planner` согласно `lab/README.md`, зафиксировать исход ответа модели и действие `POST /assistant/execute`.
  - Прямая проверка инструментов: отправить изготовленный JSON в `/assistant/execute` без токена для `export_profiles` и `delete_tree`.

- Артефакты этапа
  - REPORT_01: краткое описание угроз, PoC, ожидаемая/фактическая защита, влияние, шаги воспроизведения.
  - Логи и ответы запросов, скриншоты/файлы LLM‑запусков в `evidence/before/`.

Этап 2. Исправления и защита

- План изменений (минимальные правки, сохранить функциональность из `lab/README.md`)
  - Параметризовать SQL для `/profile`, `/search`.
  - Авторизация и сужение данных: 
    - `/orders` — только сессия пользователя и только его заказы.
    - `/admin/export` — только роль `staff` из серверной сессии, игнорировать `X-Role` клиента.
  - Валидировать бизнес‑инварианты: игнорировать клиентский `price` в `/orders`, брать цену из каталога.
  - Ограничить файловый доступ: `/files` — текущий пользователь из сессии, запрет traversal внутри чужих директорий.
  - Защитить чувствительные логи: скрыть/маскировать токены, ограничить `/debug/logs` ролью `staff` или убрать эндпоинт.
  - Санитизировать HTML в `/reviews/view` или отдавать только текст (escape).
  - Защитить ассистента: 
    - `/assistant/execute` — требовать валидную сессию; ограничить инструменты по ролям;
    - валидация путей для `read_file`/`delete_tree`; deny by default.

- Реализация фиксов
  - Внести точечные изменения в `service.py` с комментариями к нетривиальным местам.
  - Добавить/обновить unit‑тесты, покрывающие обнаруженные атаки (до фикса — красные; после — зелёные).
  - Обновить `judge-system-prompt.md` под роль Судьи: критерии отказа инструментам, политика «минимально необходимого».

- Проверки
  - Запуск `make test` и ручные проверки ключевых маршрутов.
  - Проверка границы стенда: операции с файлами остаются внутри Sandbox (не модифицировать `sandbox.py`).

Этап 3. Повторная проверка (после фиксов)

- Повторить все эксплойты из этапа 1 — сохранить результаты в `evidence/after/`.
- Prompt injection сценарии: повторный запуск `shop-planner` и принудительная передача опасного решения в `/assistant/execute` для проверки серверной защиты.
- Регрессионные тесты и негативные кейсы проходят; обычные пользовательские сценарии из `lab/README.md` сохраняются.
- REPORT_02: список атак, которые предотвращены/смягчены; остаточные риски; рекомендации.

### Отчёты и артефакты

- REPORT_01 и REPORT_02 — в корне практики или текстом в PR; ссылки на `evidence/*`.
- Модель угроз — любая форма: markdown/mermaid/plantUML/скриншот.

### Технические заметки

- Сервис всегда на `127.0.0.1`. Не обращаться к внешним сервисам.
- Не расширять границы стенда и не менять `sandbox.py`.
- Все шаги фиксировать в `REPORT.md` согласно базовым требованиям.
